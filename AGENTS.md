# Правила работы агента

- После каждой завершенной задачи перед финальным коммитом увеличивать patch-версию приложения на 1 в `backend/Directory.Build.props` (`VersionPrefix`, формат `major.minor.patch`). Например, `1.0.1` -> `1.0.2`.
- Если пользователь явно просит изменить major или minor, следовать его указанию; иначе увеличивать только patch.
- Если версия уже была увеличена в рамках текущей задачи, повторно ее не поднимать.
- Коммиты делать с логичным сообщением на русском языке.

## Git: ветки и Pull Request'ы

Обязательно для всех агентов (Codex, Claude Code) и людей. PR — Pull Request (в GitLab — Merge Request). Базовая ветка: `main`.

Особенности этого репозитория:
- Хостинг — GitHub (`Xsenus/PulsCRM`), CLI — `gh`.
- CI на PR нет. Единственный workflow `.github/workflows/deploy.yml` («Deploy Production») запускается на push в `main` и **деплоит в production** (IIS). Поэтому мерж PR в `main` — это выкладка на прод, а условие «проверки зелёные» для PR означает зелёные локальные «Проверки перед PR». После мержа проверь результат запуска «Deploy Production» (`gh run list --workflow deploy.yml`, `gh run view <id> --log-failed`).

### Ветки
- Любое изменение — даже одна строка или документация — делается в новой ветке от свежей `main`: `git fetch`, затем ветка от `origin/main`.
- Одна задача — одна ветка. Имя — по схеме, принятой в репозитории (`feature/…`, `fix/…`, `chore/…`).
- Перед созданием ветки проверь `git status`: чужие незакоммиченные изменения не трогай и не переноси в свою ветку — спроси.
- В чужие ветки, включая ветки другого агента, без запроса не коммить. Если Codex и Claude работают одновременно, у каждого своя ветка и свой worktree или клон.
- Прямые коммиты и пуши в `main` запрещены.

### Мерж — только через PR
- Изменения попадают в `main` только через PR. Запрещено: локальный `git merge` в `main` с последующим push, прямой push, force-push в общие ветки, мерж в обход защиты ветки (`--admin` и т. п.).
- Перед открытием PR прогони «Проверки перед PR». Не пиши, что проверки прошли, если ты их не запускал.
- В описании PR: что сделано и зачем, как проверено, есть ли изменения схемы БД (см. «БД и миграции»).
- Открыв PR, дождись результатов CI (`gh pr checks <номер> --watch`), если для PR появятся проверки; пока их нет — опирайся на локальные.
- PR вливается, только когда проверки зелёные (если CI нет — локальные), конфликтов нет и получены обязательные ревью. Способ мержа (squash / merge / rebase) — как принято в репозитории.
- Кто вливает: агент сам, через PR (`gh pr merge`), как только выполнены условия выше.
- Если для push или создания PR нужно подтверждение — запроси его. Если это невозможно (нет сети, прав или CLI), не обходи локальным мержем: доведи ветку до зелёных локальных проверок и в ответе дай имя ветки, заголовок и описание PR. Если среда сама создаёт ветку и PR (облачные задачи Codex и Claude Code) — пользуйся её механизмом.

### Если проверки (локальные или CI) или мерж не проходят
- Цель — зелёный PR за счёт исправления причины, а не обхода проверок.
- Читай логи упавших джобов (`gh run view <id> --log-failed`), воспроизводи падение локально той же командой, что в CI, ищи корневую причину.
- Исправляй код, а не проверки. Без явного разрешения пользователя нельзя: пропускать, удалять или ослаблять тесты; добавлять подавления ради зелёного статуса (`@ts-ignore`, `eslint-disable`, `# type: ignore`, `# noqa`, `#pragma warning disable`, skip у тестов); снижать пороги (покрытие и т. п.); править конфиги CI и линтеров, чтобы стало зелёным; коммитить с `--no-verify`.
- Тест устарел из-за намеренного изменения поведения — обнови его и объясни это в описании PR.
- Конфликты: подтяни свежую `main` в свою ветку, разреши конфликты, сохранив чужие изменения, снова прогони проверки. После rebase — только `git push --force-with-lease` и только в свою ветку.
- Исправления пушь в ту же ветку, новый PR не создавай.
- Падение не связано с твоими изменениями (то же падает на `main`, флейк, инфраструктура, секреты CI, лицензия DevExpress `DX1001`) — не маскируй его: перезапусти джоб один раз, не помогло — сообщи с диагнозом.
- После трёх циклов исправлений проверки всё ещё красные — остановись и опиши, что пробовал и в чём, по-твоему, причина.

### После мержа: удаление веток
- Удаляй ветку, только когда она полностью отработана: PR в статусе merged (`gh pr view <номер> --json state`), работы по ней не осталось и других открытых PR из неё нет.
- Удалённую ветку удали, если хостинг не сделал этого сам: `git push origin --delete <ветка>`.
- Локально: `git switch main && git pull --ff-only`, затем `git branch -d <ветка>`. После squash- или rebase-мержа git может отказаться — тогда, убедившись, что PR merged, используй `-D`. В конце `git fetch --prune`.
- Слитую ветку не переиспользуй: доработки и исправления после мержа — в новой ветке от свежей `main`.
- Никогда не удаляй `main`, защищённые и чужие ветки, а также ветки с открытыми PR или с коммитами, не вошедшими в слитый PR.

### БД и миграции
- Отдельного инструмента миграций в проекте нет. Базы и их схемы:
  - `LegacyDb` (SQL Server) — legacy-таблицы `set_*`, открываются с `SchemaAlreadyExists`: их схему из этого проекта не меняй.
  - `MailingDb` (SQL Server) — таблицы `Mail*`, создаются и дополняются XPO по моделям из `backend/src/PulsNext.Domain.Mailing` (`MailingDb:AutoCreateSchema`, по умолчанию `true`).
  - `ChatDb` (PostgreSQL, отдельная база) — таблицы `Chat*`, создаются и дополняются XPO по моделям из `backend/src/PulsNext.Domain.Chat` (`Chat:AutoCreateSchema`). Чат подключается, только если `Chat:Enabled=true` и задана строка `ConnectionStrings:ChatDb`; иначе API к PostgreSQL не обращается.
- Изменения схемы `Mail*` и `Chat*` делай только через эти модели, в той же ветке и том же PR, что и код, и явно опиши их в описании PR (новые таблицы/колонки, нужны ли ручные действия на проде).
- XPO не удаляет и не переименовывает колонки: переименование свойства — это новая колонка, старые данные остаются в прежней. Такие изменения согласуй отдельно.
- Из рабочей ветки ничего не применяй к общим и боевым базам: не запускай API из рабочей ветки с `AutoCreateSchema=true` против общей или production БД — только против локальной копии (для `ChatDb` — локальный PostgreSQL).

### Проверки перед PR
Те же команды, что выполняет `.github/workflows/deploy.yml` (до шага деплоя):

Бэкенд (.NET 9, из корня репозитория):
- `dotnet restore backend/PulsNextMailing.sln`
- `dotnet test backend/PulsNextMailing.sln --configuration Release --no-restore` (собирает решение и гоняет `backend/tests/PulsNext.Infrastructure.Tests`)
- `dotnet list backend/PulsNextMailing.sln package --vulnerable`
- При ошибке `DX1001` см. `docs/devexpress-license.md`.

Фронтенд (React + Vite, в `frontend/puls-next-web`, lock-файл `package-lock.json`):
- `npm ci`
- `npm test` (vitest)
- `npm audit --audit-level=moderate`
- `npm run build` (`tsc -b` — проверка типов — и `vite build`)

Линтеров и форматтеров (ESLint, `dotnet format`) в проекте нет — новые инструменты без согласования не добавляй. E2E-тесты (`npm run test:e2e`, Playwright) в CI не входят; запускай их, если менял сценарии, которые они покрывают.
