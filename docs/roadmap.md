# Roadmap PulsCRM

Дата актуализации: 2026-06-22.

Этот документ является единственным актуальным roadmap проекта. Старый подробный план и отдельная сводка статуса объединены здесь, чтобы в одном месте было видно, что уже сделано, что еще не закрыто и какие следующие шаги нужны для формального закрытия MVP.

## Текущий статус

Проект находится в состоянии MVP-ready, но roadmap еще не закрыт формально. Основные P0/P1-задачи по БД, рассылкам, организациям, UI/UX, адаптивности, тестам и эксплуатации реализованы и подтверждаются автоматическими проверками. Для окончательного закрытия нужна ручная приемка по checklist, подтвержденный production/IIS smoke и решение по P2/P3-остаткам.

## Сделано

### База и backend

- Основная runtime-БД переведена на SQL Server.
- SQLite убран из рабочего контура.
- `LegacyDb` и контур рассылок работают с общей SQL Server БД.
- Таблицы рассылок приведены к `Mail*`-схеме: `MailCampaign`, `MailDispatchItem` и связанные сущности.
- Фоновая обработка рассылок перенесена внутрь API.
- Добавлены сервисы диагностики очереди, восстановления отправок, статистики и проверки storage.
- Backend покрыт unit-тестами для кампаний, получателей, расписания, очереди, восстановления, composer, статистики, удаления и storage diagnostics.

### Рассылки

- Реализован рабочий end-to-end контур рассылок: SMTP-профили, кампании, получатели, шаблон письма, вложения, расписание, readiness, очередь, статистика и диагностика.
- Добавлены проверки SMTP-профилей, failure-сценарий и локальный DB/E2E smoke против SQL Server `ILYA\SQL2016 / PulsBaseDB`.
- В UI закреплены списки кампаний, настройки SMTP, очередь, диагностика dispatch, карточка кампании и статистика.
- Для ключевых переключателей и вкладок рассылок добавлены доступные подписи и тесты.

### Организации

- Большой `OrganizationRecordWorkspace` разделен на специализированные компоненты.
- Карточка организации доведена до рабочего layout: summary/sidebar, профиль, директор, банк, сопровождение, связи, история, снимки, события и legacy notes.
- Добавлены вкладки, режимы просмотра, preview-карточки связей и адаптивное поведение.
- Список организаций получил устойчивые фильтры, карточный мобильный режим и единые table-паттерны.

### UI/UX и адаптивность

- Введены общие паттерны `DataTable`, `RowActionsMenu`, `StatusBadge`, `SearchPanel`, `Pagination`, `ActionIcon`.
- Browser `window.confirm` заменен на modal-паттерны в ключевых сценариях.
- Действия строк стали компактными и доступными с клавиатуры.
- Основные рабочие экраны проверяются на narrow-mobile, mobile, tablet, desktop и wide desktop.
- Улучшены сообщения login/network error и стабильность отображения дат.

### Тесты и эксплуатация

- Добавлены frontend unit/component tests и Playwright smoke tests.
- Добавлен backend test project в solution.
- Настроены проверки `npm test`, `npm run test:e2e`, `npm run build`, `npm audit`, `dotnet test`, `dotnet build`, NuGet vulnerability scan и UTF-8 без BOM.
- Добавлены скрипты `smoke-mailing-e2e.ps1`, `smoke-iis.ps1`, `check-mailing-db.ps1`, `deploy-iis.ps1`, `rollback-iis.ps1`.
- IIS/autodeploy описан для Windows Server 2016 и self-hosted GitHub Actions runner.
- Добавлены manual smoke checklist, rollback/check DB инструкции и документация по production-настройкам.

## Не закрыто формально

- Не выполнен и не зафиксирован финальный ручной прогон `docs/manual-smoke-test.md` на релизной сборке.
- Не зафиксирован последний production/IIS smoke record после деплоя.
- P2/P3-остатки не размечены явно как закрытые, перенесенные в backlog или исключенные из MVP.
- Accessibility и визуальная полировка основных экранов сильно продвинуты, но остаются зоной дальнейших малых улучшений.
- Долгосрочные задачи наблюдаемости, performance tuning и эксплуатационных метрик не закрыты как отдельный production hardening этап.

## Что предстоит сделать

### Для формального закрытия MVP

1. Выполнить `docs/manual-smoke-test.md` на актуальной сборке.
2. Записать результат ручной приемки в `docs/whats-new.md` или отдельный release record.
3. После push/deploy подтвердить GitHub Actions и production/IIS smoke.
4. Зафиксировать решение по P2/P3-остаткам: закрыть, перенести в backlog или исключить из MVP.
5. Сделать финальный closing-коммит после приемки.

### Ближайший backlog

- Довести production/IIS smoke record до регулярной release-практики.
- Продолжить accessibility-полировку в менее частых сценариях.
- Добавить больше наблюдаемости для очереди рассылок и ошибок SMTP.
- Расширить performance-проверки для больших списков организаций, кампаний и dispatch items.
- Отдельно решить, нужны ли расширенные настройки рассылок, дополнительные admin-сценарии и углубленная аналитика.

## Критерий закрытия roadmap

Roadmap можно считать закрытым, когда:

- автоматические проверки проходят локально и в GitHub Actions;
- локальный DB/E2E smoke рассылки проходит против SQL Server;
- production/IIS deploy smoke подтвержден после push;
- ручной checklist выполнен и результат записан;
- остаточные P2/P3-задачи явно перенесены в backlog или исключены из MVP.

До этого статус проекта: MVP-ready, но roadmap не закрыт формально.
