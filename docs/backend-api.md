# Backend API

## Что изменено

API переведено с `Minimal API` на обычные MVC-контроллеры. Все публичные маршруты сохранены без изменения путей, поэтому текущий frontend продолжает работать на тех же URL.

Основные группы контроллеров:

- `HealthController` — проверка доступности сервиса.
- `AuthController` — вход, выбор пользователя для формы логина, профиль текущего пользователя.
- `DashboardController` — сводная статистика.
- `EmployeesController` — сотрудники и пользовательские карточки.
- `OrganizationsController` — организации, районы и справочники для редактора.
- `WorkController` — задачи из legacy-раздела «Работа».
- `TransportProfilesController` — SMTP-профили.
- `FilesController` — загрузка и скачивание файлов.
- `CampaignsController` — рассылки, предпросмотр, ручной запуск и статистика.
- `DispatchController` — диагностика очереди рассылок и операторские действия с элементами отправки.
- `DiagnosticsController` — защищенная диагностика storage, uploads и ключей Data Protection.

## Как теперь документируется API

Swagger собирается из XML-комментариев нескольких сборок:

- `PulsNext.Api` — описания контроллеров, маршрутов и query/form-моделей.
- `PulsNext.Infrastructure` — описания DTO и запросов, которые уходят в тело ответа или запроса.
- `PulsNext.Domain.Mailing` — описания перечислений модуля рассылок.

За счет этого в Swagger видны:

- русские `summary` у контроллеров и действий;
- описания query-параметров;
- описания моделей ответа и запроса;
- описание схемы Bearer-аутентификации.

## Как работает запрос

1. Клиент обращается к маршруту `/api/...` или `/health`.
2. Для защищенных маршрутов JWT проверяется middleware-аутентификацией.
3. Контроллер принимает route/query/body/form-параметры через обычную MVC-модель привязки.
4. Контроллер вызывает инфраструктурный сервис (`IAuthService`, `IEmployeeService`, `ICampaignService` и т.д.).
5. Исключения унифицировано превращаются в JSON-ответ с полем `message`.

Сопоставление ошибок:

- `UnauthorizedAccessException` → `401 Unauthorized`
- `KeyNotFoundException` → `404 Not Found`
- `ValidationException` → `400 Bad Request`
- все остальное → `500 Internal Server Error`

## Авторизация

Для Swagger и frontend используется схема `Bearer`.

Формат заголовка:

```http
Authorization: Bearer <jwt-token>
```

Маршрут `POST /api/auth/login` возвращает:

- `accessToken` — JWT для последующих запросов;
- `expiresAtUtc` — момент истечения токена;
- `user` — профиль текущего пользователя.

## Файлы и multipart/form-data

Маршрут `POST /api/files` принимает форму:

- `file` — бинарный файл;
- `isPublic` — флаг публичного доступа.

Контроллер валидирует формат `multipart/form-data`, после чего передает поток в `IFileStorageService`.

## Рассылки

Контроллер кампаний покрывает полный цикл:

- список и карточка кампании;
- создание и обновление;
- удаление;
- смена статуса;
- ручной запуск;
- предпросмотр расписания;
- предпросмотр получателей;
- статистика отправки.

Логика вычисления получателей, расписания и партий отправки остается в инфраструктурных сервисах; контроллеры только принимают HTTP-запрос, валидно связывают данные и возвращают результат в документированном контракте.

## Диагностика очереди

Контроллер `/api/dispatch` дает операторский доступ к очереди без прямого входа в SQL:

- `GET /api/dispatch/items?status=&campaignId=&batchId=&search=&skip=&take=` — список элементов очереди с пагинацией;
- `GET /api/dispatch/batches?campaignId=&skip=&take=` — список партий отправки;
- `POST /api/dispatch/items/{id}/retry` — возвращает failed/deferred/queued элемент в очередь;
- `POST /api/dispatch/items/{id}/cancel` — отменяет элемент, если письмо еще не отправлено.

`take` ограничен верхним пределом на стороне API, чтобы диагностические запросы не выгружали всю очередь за один вызов.

Frontend использует эти маршруты на странице `/dispatch`: оператор видит сообщения очереди, партии отправки, фильтры по статусу/кампании/партии, поиск по получателю/ошибке/SMTP-ответу и действия повторной постановки или отмены сообщения.

## Диагностика storage и Data Protection

Защищенный маршрут `GET /api/diagnostics/storage` проверяет серверные каталоги, которые критичны для API:

- `Keys` — каталог ключей Data Protection из настроек `Storage:RootPath` + `Storage:KeysPath`;
- `Uploads` — каталог пользовательских файлов из настроек `Storage:RootPath` + `Storage:UploadsPath`;
- `Secrets` — проверка protect/unprotect round-trip через текущий Data Protection provider, чтобы подтвердить пригодность key-ring для SMTP-паролей;
- для каждого каталога API пытается создать директорию, записать временный probe-файл, прочитать его и удалить.

Маршрут требует Bearer JWT и не добавлен в публичный `/health`, потому что возвращает абсолютные пути на сервере. Если `Keys.CanWrite=false` или `Secrets.CanProtectAndUnprotect=false`, нужно проверить права учетной записи IIS application pool или службы runner на каталог `C:\PulsCRMData\keys`. Потеря или недоступность ключей Data Protection может сделать уже сохраненные SMTP-пароли нечитаемыми.
