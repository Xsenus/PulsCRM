# Анализ состояния проекта PulsCRM

Дата анализа: 2026-06-10.

Документ фиксирует текущее состояние проекта перед составлением roadmap. Это не план работ и не список задач к немедленному выполнению. Цель - понять, что уже реализовано, где есть технические и продуктовые риски, какие формы требуют переработки, и какие проверки нужны перед доработками.

## Краткий вывод

Проект уже является рабочим full-stack приложением, а не только заготовкой. Есть ASP.NET Core API, React/Vite frontend, авторизация через legacy-пользователей, разделы сотрудников и организаций, настройки SMTP, рассылки, загрузка файлов, очередь отправки и hosted services внутри API.

При этом качество реализации неравномерное:

- раздел сотрудников выглядит наиболее зрелым и может быть эталоном для остальных списков;
- раздел организаций перегружен сложной боковой панелью, широкой таблицей и очень большой карточкой организации;
- раздел рассылок функционально собран, но визуально и сценарно выглядит как технический конструктор, а не как проверенный рабочий инструмент;
- адаптивность есть в CSS, но она не решает главный вопрос таблиц: на телефонах и планшетах таблицы остаются широкими и уходят в горизонтальный скролл;
- автоматических тестов почти нет;
- рассылки имеют полноценный backend-поток, но нет подтверждения, что он был прогнан end-to-end на реальном SMTP/тестовой БД.

## Проверки, выполненные в рамках анализа

Команды:

```powershell
npm run build
dotnet build backend\PulsNextMailing.sln
```

Результат:

- frontend успешно собирается через `tsc -b && vite build`;
- backend успешно собирается;
- при backend build есть предупреждение `NU1902`: пакет `MailKit 4.15.1` имеет известную уязвимость средней критичности;
- рабочее дерево после анализа чистое.

Ограничение анализа:

- визуальный runtime-прогон всех экранов в браузере с реальными учетными данными не выполнялся;
- выводы по верстке сделаны по структуре компонентов, CSS и уже предоставленным скриншотам/симптомам;
- для окончательной приемки нужен отдельный UI-прогон на desktop/tablet/mobile.

## Backend

### Общая архитектура

Backend построен на ASP.NET Core Web API / .NET 9.

API использует обычные MVC-контроллеры:

- `AuthController` - логин, текущий пользователь, список пользователей для формы входа;
- `DashboardController` - сводные показатели;
- `EmployeesController` - сотрудники;
- `OrganizationsController` - организации, районы, справочники;
- `WorkController` - legacy-задачи;
- `TransportProfilesController` - SMTP-профили;
- `FilesController` - загрузка и скачивание файлов;
- `CampaignsController` - кампании, preview, запуск, статистика;
- `HealthController` - `/health`.

Исключения централизованно превращаются в JSON-ответ с `message` в `Program.cs`.

### База данных

В коде есть два UnitOfWork:

- `LegacyUnitOfWork`;
- `MailingUnitOfWork`.

Это не обязательно две физические базы. По текущей целевой архитектуре обе строки подключения должны указывать на одну основную SQL Server БД:

```json
"ConnectionStrings": {
  "LegacyDb": "...initial catalog=DXPulsBase...",
  "MailingDb": "...initial catalog=DXPulsBase..."
}
```

Разница логическая:

- `LegacyDb` работает со старыми таблицами `set_*`;
- `MailingDb` работает с новыми таблицами `Mail*`.

Важно:

- для legacy используется `AutoCreateOption.SchemaAlreadyExists`;
- для mailing используется `AutoCreateOption.DatabaseAndSchema` или `SchemaAlreadyExists` в зависимости от `MailingDb:AutoCreateSchema`;
- в production example `AutoCreateSchema` стоит `false`, но в серверном гайде допускается `true` на первом запуске.

Новые таблицы рассылок:

- `MailTransportProfile`;
- `MailCampaign`;
- `MailCampaignTargetOrganization`;
- `MailStoredFile`;
- `MailCampaignAttachment`;
- `MailDispatchBatch`;
- `MailDispatchItem`.

Вывод: SQLite в текущей архитектуре не нужен. Проект уже рассчитан на SQL Server.

### Авторизация

Логин идет через legacy-пользователей. Совместимость паролей сохранена через старый MD5-подход, описанный в README.

Frontend хранит JWT в `localStorage` под ключом `puls-next-token`. При `401` токен удаляется и приложение получает событие `puls-auth-expired`.

Риски:

- хранение JWT в `localStorage` проще для текущего проекта, но уязвимее к XSS, чем httpOnly cookie;
- нет отдельного refresh-token механизма;
- нет проверки сложности `Jwt:SigningKey` на старте, кроме фактической настройки.

### Legacy-сервисы

Сервисы сотрудников, организаций, задач и dashboard работают через XPO.

Наблюдение: во многих местах данные сначала загружаются в память через `ToList()`, а фильтрация/сортировка/пагинация применяются потом:

- логин пользователей;
- список сотрудников;
- часть проверок удаления;
- список задач;
- dashboard counters;
- статистика рассылок.

Это допустимо для начального запуска на небольшой базе, но рискованно для реальной CRM, где организаций, задач и истории может быть много.

Потенциальные последствия:

- медленная загрузка списков;
- высокая память процесса IIS;
- зависания при фильтрации;
- рост времени health/runtime операций, если dashboard будет вызывать тяжелые запросы.

### Организации backend

API поддерживает:

- список организаций;
- фильтрацию по району/районам;
- справочники для редактора;
- карточку организации;
- создание/обновление;
- удаление.

Удаление проверяет связи с задачами и рассылками. Это правильно, потому что рассылки хранят ссылки на legacy organization id.

Риски:

- карточка организации возвращает много связанных коллекций;
- frontend карточки уже очень сложный, значит backend contract тоже требует аккуратного разделения на вкладки или ленивую загрузку;
- нет отдельного API для частичного обновления секций карточки.

### Рассылки backend

Реализованы основные сущности и сценарии:

- CRUD кампаний;
- CRUD SMTP-профилей;
- загрузка файлов;
- сохранение вложений;
- preview расписания;
- preview получателей;
- ручной запуск;
- смена статуса;
- статистика кампании;
- фоновая постановка due campaigns в очередь;
- queue pump;
- sender workers;
- recovery зависших задач;
- retry с экспоненциальной задержкой.

Hosted services подключены внутри API:

- `SchedulerHostedService`;
- `QueuePumpHostedService`;
- `RecoveryHostedService`;
- `SenderHostedService`.

Это соответствует требованию убрать отдельный worker service.

Поток рассылки:

1. Кампания становится `Active`.
2. Scheduler находит кампании с наступившим `NextRunAtUtc`.
3. DispatchService создает `MailDispatchBatch`.
4. Для получателей создаются `MailDispatchItem`.
5. QueuePump резервирует due items и пишет их в in-memory channel.
6. SenderHostedService читает channel и отправляет письма через MailKit.
7. Успех/ошибка записываются в `MailDispatchItem`.
8. Batch counters пересчитываются.
9. Recovery возвращает зависшие элементы в очередь.

Сильные стороны:

- есть персистентная очередь в SQL;
- есть статусы `Queued`, `Processing`, `Sent`, `Deferred`, `Failed`, `Cancelled`;
- есть retry;
- есть ограничения по SMTP-профилю: `MaxConnections`, `MessagesPerMinute`;
- пароли SMTP защищаются через Data Protection.

Риски:

- in-memory channel означает, что при нескольких IIS-инстансах или перезапуске нужна аккуратная recovery-логика;
- нет отдельного экрана общей очереди и ошибок;
- нет тестов на расчет расписания;
- нет тестов на resolver получателей;
- нет тестов на retry/recovery;
- нет тестов на отправку через fake SMTP;
- `MailKit 4.15.1` требует обновления из-за предупреждения безопасности;
- при остановке app pool отправка прерывается, а корректность возврата `Processing` зависит от Recovery.

### Файлы и хранилище

Файлы сохраняются через `FileStorageService`:

- метаданные в `MailStoredFile`;
- физические файлы в `Storage:RootPath/UploadsPath`;
- путь строится по дате `yyyy/MM/dd`;
- лимит задается `MaxFileSizeBytes`.

Риски:

- нет антивирусной/типовой проверки файлов;
- нет очистки неиспользуемых файлов;
- нет отдельного UI для управления хранилищем;
- вложения кампании удаляются из связи, но физические файлы могут оставаться.

### Деплой

Workflow: `.github/workflows/deploy.yml`.

Сценарий:

1. checkout;
2. проверка установленного toolchain;
3. `dotnet restore`;
4. `npm ci`;
5. `npm run build`;
6. `dotnet publish`;
7. `scripts/deploy-iis.ps1`;
8. healthcheck;
9. warmup.

`deploy-iis.ps1` уже решает ранее найденные проблемы:

- кладет `app_offline.htm`;
- останавливает API app pool;
- копирует через `robocopy /MIR`;
- запускает app pool;
- проверяет `/health`;
- прогревает API и frontend;
- сбрасывает `$LASTEXITCODE` после robocopy.

Риски:

- workflow жестко использует warmup frontend `http://localhost:8080/`;
- нет smoke-теста авторизации/API после деплоя;
- нет проверки, что frontend собран с правильным `VITE_API_URL`;
- нет backup/rollback опубликованного сайта;
- нет миграционного шага, который явно проверяет наличие таблиц `Mail*`.

Frontend:

В `package.json` README упоминает DevExtreme React, но фактически в зависимостях его нет. UI написан кастомными компонентами.

Активные маршруты:

- `/employees/:id/edit`;
- `/organizations`;

Проблема:

- в меню `AppShell` раздела "Работа" нет;
- backend API `/api/work` есть.

Нужно принять продуктовое решение: возвращать раздел задач или убрать мертвый frontend-код.

### Общие компоненты

#### AppShell

Есть sidebar, topbar, профиль пользователя, collapse sidebar. На desktop это нормальная основа.

Риски:

- на планшетах sidebar становится обычным блоком сверху, что может занимать много высоты;
- нет burger/drawer-паттерна для мобильных;
- текущий визуальный язык довольно "карточный" и мягкий, для CRM можно сделать плотнее.

#### PageHeader

Простой компонент. Хорошая база.

Риск:

- если в actions много кнопок, header быстро ломается на мобильных;
- в рассылках actions уже перегружены.

#### SearchPanel

Хороший общий компонент:

- search;
- clear;
- refresh;
- debounce.

Проблема:

- применяется не везде одинаково;
- организации передают дополнительные className и содержат старый мертвый search JSX.

#### DataTable

Сильные стороны:

- настройки колонок через `localStorage`;
- скрытие колонок;
- изменение ширины;
- drag reorder;
- loading overlay;
- selected row;
- context menu hook.

Проблемы:

- таблица всегда остается таблицей;
- `tableMinWidth` минимум 920 для configurable таблиц;
- на телефоне это почти всегда горизонтальный скролл;
- нет режима mobile cards;
- нет стандартного action menu для строк;
- нет встроенного column priority для mobile/tablet;
- настройки колонок сохраняются, но не решают адаптивность;
- в модалке настроек таблицы много текста, вероятен перегруз на телефоне.

#### Pagination

Сильные стороны:

- есть `pageSizeOptions`;
- есть dropdown выбора размера страницы;
- есть page buttons.

Проблемы:

- на телефоне много элементов, они уходят в вертикальный стек;
- нет компактного режима "предыдущая / следующая / страница N из M";
- в организациях используется локальная копия `PAGE_SIZE_OPTIONS`, а не общий `app/table.ts`;
- есть риск, что пользователь воспринимает "отображать строки" как неработающее из-за визуального расположения или localStorage ключей.

#### Modal

Простая модалка с maxWidth. Работает как база.

Риски:

- большие формы в модалке на мобильном могут быть неудобны;
- SMTP profile modal нужно проверить на высоте 720px и ниже.

### CSS и адаптивность

В `styles.css` есть media queries:

- `max-width: 1200px`;
- `max-width: 980px`;
- `max-width: 720px`.

Есть адаптивные grid rules для многих блоков. Но проблема не в полном отсутствии media queries, а в том, что главные рабочие поверхности остаются широкими:

- `DataTable` min-width 640/920;
- action columns с несколькими текстовыми кнопками;
- organization sidebar + main table;
- campaign editor с большими панелями;
- organization record workspace с множеством вкладок и sidebar.

На телефонах и планшетах нужны не только CSS-breakpoints, а другие представления:

- фильтры в drawer/collapsible;
- строки таблицы как compact cards;
- row actions в меню;
- меньше одновременных панелей на экране;
- sticky save/actions для длинных форм;
- отдельные вкладки вместо длинной страницы.

## Сквозные проблемы UI

### 1. Нет единого CRUD-list стандарта

Сотрудники реализованы аккуратно. Организации, рассылки и SMTP отличаются.

Нужен стандарт:

- `PageHeader`;
- `SearchPanel`;
- filter panel;
- `DataTable`;
- row selection;
- row actions;
- `Pagination`;
- delete modal;
- mobile card view.

### 2. Таблицы не адаптивны по смыслу

CSS делает контейнеры адаптивными, но таблицы остаются широкими.

Нужен responsive table strategy:

- desktop: table;
- tablet: table с сокращенным набором колонок;
- mobile: cards/list rows;
- actions: context menu;
- page size: compact control.

### 3. Слишком много текстовых кнопок в строках

Особенно:

- рассылки;
- SMTP-профили.

Это ломает ширину и визуальный ритм.

### 4. Есть `window.confirm`

Используется в рассылках и SMTP. В проекте уже есть `Modal`, поэтому confirm выглядит неаккуратно и выбивается из интерфейса.

### 5. Много крупных монолитных компонентов

Самые крупные:

- `OrganizationRecordWorkspace.tsx`;
- `EmployeeEditorForm.tsx`;
- `CampaignEditPage.tsx`;
- `DataTable.tsx`;
- `OrganizationsPage.tsx`;
- `TransportProfilesPage.tsx`.

Часть крупных компонентов оправдана, но `OrganizationRecordWorkspace` и `CampaignEditPage` стоит разделить для сопровождаемости и будущих правок.

### 6. Недостаточная диагностика ошибок

Пользователь видит toast или `Network Error`, но часто не понимает:

- API недоступен;
- нет CORS;
- токен истек;
- SMTP не настроен;
- нет получателей;
- нет файлов;
- кампания не готова.

### 7. Нет пустых/ошибочных состояний уровня продукта

Есть generic empty states, но рассылкам нужны специальные состояния:

- нет SMTP-профиля;
- нет получателей;
- нет email у выбранных организаций;
- нет активных кампаний;
- очередь пуста;
- есть failed items.

## Сквозные проблемы backend

### 1. Нет тестов

Особенно критично для:

- `ScheduleCalculator`;
- `RecipientResolver`;
- `DispatchService`;
- `MailComposer`;
- `TransportProfileService`;
- auth compatibility;
- organization delete constraints.

### 2. Много in-memory фильтрации

Использование `ToList()` до фильтрации/пагинации надо пересмотреть для больших таблиц.

### 3. Нет отдельного админского API по очереди

Сейчас статистика доступна по кампании, но нет общего списка:

- все failed items;
- все deferred;
- последние ошибки;
- зависшие processing;
- ручной retry/cancel.

### 4. Нет явного migration/check step

XPO может создавать схему, но для production полезно иметь:

- SQL-check таблиц `Mail*`;
- проверку индексов;
- документированный первый запуск;
- выключение `AutoCreateSchema` после создания.

### 5. Нет наблюдаемости

Нет отдельной телеметрии:

- structured logs по CorrelationId;
- метрики queue depth;
- метрики SMTP errors;
- dashboard health фоновых задач.

## Риски для продакшена

Высокие:

- рассылки не покрыты end-to-end тестами;
- нет UI для общей диагностики очереди и ошибок;
- таблицы и формы плохо адаптируются под mobile/tablet;
- organization workspace слишком сложный и может ломаться при малых ширинах;
- in-memory фильтрация может тормозить на большой базе;
- `MailKit` имеет warning по известной уязвимости.

Средние:

- workflow не проверяет бизнес-сценарии после деплоя;
- нет rollback;
- `window.confirm` и разнородные модалки ухудшают UX;
- часть страниц/кода не включена в навигацию;
- `Europe/Amsterdam` как timezone по умолчанию выглядит ошибочно для проекта.

Низкие:

- повторение `PAGE_SIZE_OPTIONS` в нескольких местах;
- мертвый JSX в `OrganizationsPage`;
- текстовые символы в combobox логина;
- placeholder вкладка "Основные" в настройках.
