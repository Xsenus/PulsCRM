# Roadmap правок PulsCRM

Дата составления: 2026-06-10.

Основа: `docs/project-analysis.md`.

Документ описывает рекомендуемый порядок доработок проекта. Roadmap специально сделан подробным: его можно разбирать на issue, pull request или рабочие спринты. Приоритеты указаны с точки зрения практического запуска проекта на локальном IIS/SQL Server и доведения интерфейса до нормального CRM-качества.

## Цели roadmap

Главные цели:

1. Привести интерфейс к единому качеству, где разделы организаций и рассылок не выглядят хуже сотрудников.
2. Сделать приложение удобным на desktop, tablet и phone.
3. Проверить и довести рассылки до рабочего end-to-end сценария.
4. Убрать очевидные технические риски перед дальнейшим расширением.
5. Добавить минимальные проверки, чтобы правки не ломали уже работающие сценарии.

Не цели первого roadmap:

- полная замена архитектуры;
- переход на другую ORM;
- вынесение очереди в RabbitMQ/Redis;
- полноценный redesign с нуля;
- миграция всей legacy CRM.

## Приоритеты

### P0 - блокирует нормальную работу

- ошибки, из-за которых пользователь не может выполнить основной сценарий;
- рассылки нельзя проверить end-to-end;
- формы ломаются или становятся непригодными на типовых экранах;
- deploy проходит, но приложение после него неработоспособно.

### P1 - критично для качества MVP

- плохой UX в ключевых разделах;
- отсутствие диагностики;
- большие технические риски;
- неунифицированные CRUD-паттерны;
- отсутствие минимальных тестов.

### P2 - важно, но можно после стабилизации

- улучшение визуальной полировки;
- рефакторинг крупных компонентов;
- расширенная наблюдаемость;
- улучшение производительности не самых горячих мест.

### P3 - можно отложить

- дополнительные удобства;
- расширенные настройки;
- неосновные админские сценарии.

## Этап 0. Зафиксировать базовую точку

Цель: перед изменениями получить воспроизводимое состояние проекта и минимальный набор ручных проверок.

Приоритет: P0.

### 0.1. Зафиксировать окружение

Задачи:

- записать фактический production/local адрес API;
- записать фактический frontend URL;
- записать SQL Server instance и БД;
- убедиться, что `LegacyDb` и `MailingDb` указывают на одну нужную SQL Server БД;
- убедиться, что SQLite нигде не используется в runtime;
- проверить наличие таблиц `Mail*` в локальной тестовой БД;
- проверить, что `AutoCreateSchema` в production будет выключен после создания схемы.

Готово, если:

- есть актуальный локальный `appsettings.Production.json` вне Git;
- `/health` отвечает через IIS;
- frontend открывается по IP/порту;
- логин работает;
- SQL содержит ожидаемые `Mail*` таблицы.

### 0.2. Создать чеклист ручного smoke-теста

Задачи:

- добавить документ `docs/manual-smoke-test.md`;
- описать минимальные шаги:
  - login;
  - dashboard;
  - employees list;
  - organizations list;
  - campaign list;
  - SMTP profiles;
  - healthcheck;
  - deploy warmup.
- добавить отдельный блок для рассылок:
  - создать SMTP-профиль;
  - проверить SMTP-профиль;
  - создать тестовую кампанию;
  - выбрать тестовую организацию;
  - preview получателей;
  - preview расписания;
  - сохранить;
  - ручной запуск;
  - проверить batch/items в UI/SQL.

Готово, если:

- чеклист можно выполнить после каждого деплоя;
- результат теста можно отметить вручную.

### 0.3. Проверить сборку и предупреждения

Задачи:

- запускать `npm run build`;
- запускать `dotnet build backend\PulsNextMailing.sln`;
- зафиксировать warning `MailKit 4.15.1`;
- решить, обновляем ли `MailKit` сразу или отдельным PR.

Готово, если:

- сборка зеленая;

- `dotnet build backend\PulsNextMailing.sln` проходит;
